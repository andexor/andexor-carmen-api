# andexor-carmen-api

Read, in this order, before doing anything here:

1. `andexor-carmen-main/CLAUDE.md`: the standing conventions for the three Carmen repos.
2. `andexor-carmen-main/PRD.md`: the master Product Requirements Document (PRD).
3. `andexor-carmen-main/db/README.md`: the common data model. Use its names unchanged.
4. `PRD.md` in this repo: what this app must do. It refines the master and may not contradict it.
5. `specs/` in this repo, starting with `specs/000-repo-setup/spec.md`: what changed since the PRDs were frozen. Where a spec and a PRD differ, the spec governs. Also read `andexor-carmen-main/specs/001-review-open-items/decisions.md`.
6. `.specify/memory/constitution.md`: copied from `andexor-carmen-main`. Do not edit it here.

Work follows Spec Kit: specification, plan, tasks, implement. The feature backlog is the last section of `PRD.md`; specify features in that order. Spec folders `001` to `016` carry the backlog's numbers.

A change that conflicts with the master PRD or the data model starts with a pull request in `andexor-carmen-main`.

## Working in this repo

- Python with `uv`; Wrangler only through `uv run pywrangler`; other Cloudflare resources through the `cf` CLI. No Bun, no Docker.
- `wrangler.jsonc` holds production at the top level and the preview Worker under `env.preview`. Bindings, `vars`, and `routes` must be repeated under `env.preview`: a preview that inherits the production route or database would touch production. It stays plain JSON with no comments, because scripts edit it.
- A binding is added to `wrangler.jsonc` by the feature that first uses it, in both environments.
- This repo holds no schema. Migrations and their runner are in `andexor-carmen-main` (`db/carmen/`, `tools/migrate.py prev|prod`). Runtime code never issues Data Definition Language (DDL).
- Both hostnames are behind Cloudflare Access, so a plain `curl` gets a sign-in redirect or 403. Use `./health.sh`, which sends the service token from `.env`. The token is allowed on the preview only.
- Scripts are listed in `README.md`. `preview-test.sh` is the smoke test; each feature adds its calls to it.
- Nothing is deleted on the preview by a test, ever (`specs/030-keep-preview-data/spec.md`): not by `preview-test.sh`, the pipeline, `ai-test.sh`, or a test run by hand. Test data stays for Ed to review. A smoke test or regression test never calls a delete endpoint, not even to check a refusal; the endpoints themselves work as always. A new smoke test step gives its names and websites the tag of the run and adds no cleanup.
- A manual step on Cloudflare or GitHub goes in `MANUAL-TASKS.md`.
- Roles are enforced, deny by default (`specs/001-skeleton-and-pipeline/spec.md`). Every endpoint goes in `src/app.py` with `@action(READ)`, `WRITE`, `DELETE`, or `MANAGE` under the route decorator; a route without one is refused with 403 and fails `./unit-test.sh`. List the action of each endpoint in every feature spec.
- The API's contract is the OpenAPI 3.1 document that FastAPI generates, served at `/api/openapi.json` with the Swagger UI at `/api/docs` (`specs/031-openapi/spec.md`). Both are routes with `@action(READ)`, added by the class `Api` in `src/app.py`; never let FastAPI register its own documentation routes, because those skip `authorize`. Every route declares `response_model`, its real `status_code`, and `@takes(<body model>)` under `@action` when it has a body (`specs/032-openapi-models/spec.md`). The models of stored records and of record bodies are `src/models.py`, generated by `python3 tools/gen_models.py` from the migrations in `andexor-carmen-main` and the field lists in `src/records.py`: never edit it, and run the generator after a migration or a field list change, or `./unit-test.sh` fails. Anything that is more than one record goes in `src/contract.py`. A model only describes: handlers still build their own answers and check their own bodies. The smoke test checks every answer against the specification (`tools/contract_check.py`), so a new route needs a smoke test call. `describe` adds the tag, the action, and the real errors to every operation.
- The identity of the caller is `request.state.identity` (the `app_user` row plus `machine`). A service token is a machine caller with the role `MACHINE`: it may call the machine methods and nothing else, in every environment, and it has no `app_user` row. The preview's test token alone acts as `ADMIN` (`SERVICE_TOKENS_ARE_ADMIN`, never set for production).
- The Workers runtime returns a D1 row as a Python dict, and no row as a false value. Do not call `to_py()` on it.
- More D1 facts, proven in feature 002: `bind(None)` stores NULL; `all()` returns a dict with a `results` list; `batch([...])` takes a Python list, runs as one transaction, and returns one such dict per statement; `RETURNING *` works. D1 enforces foreign keys by itself, so no `PRAGMA foreign_keys` is issued.
- A delete that a `MEMBER` may perform on their own record declares `@action(WRITE)` and then calls `may_delete(request, owner_id)` (`specs/003-activities-and-tasks/spec.md`, FR-017). Every other delete declares `@action(DELETE)`.
- Dates are put in ISO 8601 form before they are stored, in every endpoint: `records.clean` does it for any body field named `*_date` or `*_at`. Pass a date query filter through `records.iso_date` or `records.iso_timestamp` yourself.
- All score arithmetic is in `src/scoring.py`, which is pure. A feature that changes answers, the rubric, or a service stores scores through `score_writes` or `rescore_all` in `src/app.py`, never with its own SQL. A writer of scores reads the company (`SCORED_COMPANY`), its answers, and the rubric in one batch through `read_for_scoring`, and puts `score_writes` in the same batch as its change (`specs/039-score-version-mark/spec.md`): the batch fails when another writer wrote the company's scores since that read. On a failure the writer asks `score_moved`, and reads again and redoes its work when the mark moved, at most `SCORE_TRIES` times; `set_answers` shows the pattern. Never read the rubric or the answers in a separate call from the company's mark.
- A change that changes every score (a rubric question, a service's `offered` or `active`, a `score.*` setting) puts `rescore_mark(database)` in the same `batch` as the change, then calls `rescore_all` (`specs/034-rescore-retry/spec.md`). The mark is the setting `rescore.requested`; `rescore_all` clears it, and the scheduler's step `rescore` rescores while it is set. A new endpoint of that kind MUST do the same.
- Points say how good an answer is, in Fit and in Need alike. `score` turns that into Need: the share of points not earned (`specs/022-need-direction/spec.md`). Do not give a Need question `invert` to get that effect, and do not turn Need around anywhere else.
- A measured criterion (`specs/021-measured-criteria/spec.md`) is a yes-or-no question with `yes_at` in its `config_json` and a fact named by `enrichment_key`. Code answers it from the fact (`scoring.from_fact`), and a scoring run never sends it to a model. The limit is data, set by a migration in `andexor-carmen-main`, never a constant in code.
- Every edit and every delete of a stored record is recorded (`specs/018-change-log/spec.md`): the Worker log first, then the company's timeline. `audit(...)` writes the log line when it is called and returns the timeline statements, which go first in the same `batch` as the change. It returns none when the record has no company, and then the Worker log is the only record. A stage or score change calls `log_change(...)` and writes its own timeline entry. A new endpoint that changes or deletes a record MUST do the same.
- A trigger that runs after a write (a deal's `closed_at`) is not visible in `RETURNING`. Read the row back after the batch.
- Python inside a Worker has no time zone data of its own. The `tzdata` package supplies it, so `zoneinfo` works the same in a Worker and in the unit tests. Use `zoneinfo` in pure code (`records.local_date`), never the Worker's clock zone or the runtime's `Intl`.
- Bytes given to a binding (R2 `put`) MUST be a JavaScript `ArrayBuffer`: `to_js(data).buffer`. The Workers Python layer checks every value passed to a binding and walks anything iterable one item at a time, so a `Uint8Array` or `bytes` of 1 MiB costs about 4 seconds and larger ones exceed the CPU limit. Measured in feature 008.
- Documents: the R2 object is written first, then the row; the row is deleted first, then the object. A company with agreements or documents cannot be deleted.
- Work that outlasts a request goes through the `RUNS` queue, never `wait_until`: work started after a response is cut off at about 30 seconds, and a queue consumer ran 200 seconds (discovery D2, `specs/009-ai-runs/spec.md`). The queue handler is in `src/worker.py`; it has no request, so it uses `env` directly and must not raise.
- A CSV import (`specs/013-csv-import/spec.md`) runs on the `RUNS` queue too: a message holds `import_id` or `run_id`, and `src/worker.py` tells them apart. Its file and its result are objects in `DOCS` under `imports/<id>/`, because `import_batch` holds only counts. The rules for a file, a mapping, and a row are in `src/imports.py`, which is pure.
- A D1 `batch` counts as one query against the limit for one invocation, so many rows are written as a few batches, never one query per row.
- A buffered response is not sent until the ASGI application returns, so FastAPI `BackgroundTasks` delay the response. Do not use them.
- A new AI provider is one adapter class in `src/ai.py`, registered in `ADAPTERS`. Everything a model returns goes through `clean_facts` or `clean_answers` before it is stored.
- The smoke test and the pipeline MUST NOT call a paid model. They use the stub. A real model is tried on the preview with `./ai-test.sh run <model id>`, on demand; it costs money, so run it when an adapter, a prompt, or a model changed, and say what it cost.
- A provider's API key is a Secrets Store binding (`await env.CLAUDE_API_KEY.get()`), bound in both environments. It is never logged, stored, or returned, and a provider's error message stays in the log.
- Prompts are files in `src/prompts/`, packaged by the `rules` entry in `wrangler.jsonc` and read with `ai.render`. Text from outside (company records, dossiers, web pages) goes between tags and is declared to be data, not instructions.
- A run MUST NOT fall back to another model silently: runs are compared per model, so a refusal fails the run. A job may then start a new run with the next model, as the proposals job does (`first_success` in `src/app.py`): the failed run stays failed, and every run is logged and listed in the job's email.
- The `AI` binding takes a Python dict and returns a Python dict: `await env.AI.run(model_id, body)`. Do not convert the reply with JavaScript `JSON.stringify`; that gives an empty object. Every Workers AI text model answers in the chat completion shape, so `ai.WorkersAI` has no per-model code. A new model needs only its row and, when its context is not 24,000 tokens, an entry in `WORKERS_AI_CONTEXT`.
- A model that cannot search reads the company's own website through `src/pages.py`. Only a public address on the same site is fetched, and page text reaches a model only between `pages` tags. A page that is left out gets a short reason that is safe to show (`specs/020-page-fetch-reasons/spec.md`): it goes into the run's failure message, or into the timeline entry when the run succeeds, and the detail goes to the Worker log.
- Two runs of `./ai-test.sh run` at the same time need different websites: two companies cannot share one. The test company stays on the preview, and a later run with the same website uses it again.
- Jev (provider `TYPESAFE`) scores only and is tried with `./ai-test.sh run <Jev id> --research <model id>`. It gives judgments and code decides: the question wording and the thresholds are together in `src/ai.py` (`YES_AT`, `NO_AT`, `ANSWERABLE_AT`, `RATING_LEVELS`). An unsettled judgment is left unknown, never guessed, and a failed call is an error, never an answer. Do not fit a threshold to a few cases.
- Jev is pinned to a numbered version in its `ai_model` row (`jev-1.14.0`), never an alias such as `jev-latest` (`specs/027-pin-jev-version/spec.md`). Whenever work touches AI, compare it with `https://docs.typesafe.ai/models.md`. When a newer numbered version exists, read the changelog and the jaggedness page, tell Ed what changed and whether data or logic here must change, and wait for the decision. An upgrade is one coordinated change: a migration in `andexor-carmen-main`, the code and tests, and a real comparison run on the preview.
- A provider key is one more entry in `secrets_store_secrets`, in both environments: `CLAUDE_API_KEY` and `TYPESAFE_API_KEY`.
- Writes reuse the helpers in `src/app.py` (`insert`, `update`, `unknown_code`, `failed`, `db_status`, and `page` for lists; pass `stamp=False` to `update` for a table with no `updated_at`) and the field lists in `src/records.py`. A write that needs two statements uses `batch`. Each database call sits in its own inline try/except that names its step.
- The machine methods (`specs/014-machine-methods/spec.md`), `create_lead` and `add_facts` in `src/app.py`, are written once with no request. Each has two doors: a method on the entry point in `src/worker.py` for a Worker that calls over a Service Binding, and an endpoint with `@action(MACHINE)`. A change goes in the shared function, never in a door.
- A method called over a Service Binding MUST NOT raise: an exception reaches the caller with a whole traceback. It returns `ok` false with an error code and a safe message (`machine_call`). Its argument is a JavaScript object, so it is converted with `to_py()`.
- The scheduler (`specs/015-scheduler-and-notifications/spec.md`) is `run_scheduler` in `src/app.py`, written once with no request. It has two doors: the hourly Cron Trigger (`scheduled` in `src/worker.py`) and `POST /api/v1/scheduler/run`. It must not raise, and a new scheduled job is one more step in it.
- Email goes through a provider in `src/notify.py`, named by the variable `EMAIL_PROVIDER`: `CLOUDFLARE` in production, `STUB` under `env.preview`, so test data never reaches an inbox. The smoke test and the pipeline MUST NOT send a real email. Real email is tried on the preview with `./email-test.sh`, on demand. Every message goes through `notification(...)` in `src/app.py`, which records it as `QUEUED` first, sends it, and then stores the result (`specs/037-record-email-first/spec.md`). It answers the stored row, or none when another run recorded the same message since `since`; a caller never sends by itself and never stores the row itself. A row that stays `QUEUED` is named in the next digest.
- The digest is made on the days in the setting `digest.days` and is sent also when it has nothing to report (`specs/023-weekday-digest/spec.md`). Alerts and expiry run every day.
- An agreement's renewal policy has no default (`specs/024-renewal-policy/spec.md`): `ONE_TIME`, `AUTO_RENEW` (no end date), or `APPROVAL` (an end date and `term_months`). An active agreement needs a policy and an end basis; the rules are in `records.renewal_problem`, and the scheduler ends an agreement by its policy. Never give these fields a default, in code or in a test helper.
- A renewal is approved with `POST /agreements/{id}/renewal`, never by editing the end date for the person.
- The recipient of an email is the setting `digest.recipient`. Never write an address in code or in a test.
- A sender or a recipient is written `Name <address>` (`specs/028-email-names/spec.md`): `EMAIL_FROM` is `Carmen <address>` in production and `Carmen PREV <address>` under `env.preview`, and `digest.recipient` holds the recipient's name with the address. Only `records.mailbox` parses the form, and `notify.party` shapes it for the binding, which wants `email` and `name` together or a bare address. A new kind of recipient (a contact) passes the name from its record the same way.
- A subject from the preview starts with `PREV: ` (`specs/029-email-subject-prefix/spec.md`): the variable `EMAIL_SUBJECT_PREFIX` is `PREV` under `env.preview` and MUST NOT be set for production. `notification(...)` adds it, so a template and a caller never write it.
- An email's text is a file in `src/templates/email/` (first line the subject), read with `notify.render`. A `.txt` file under `src/` is packaged by default; do not add it to `rules` in `wrangler.jsonc`.
- The `send_email` binding takes a JavaScript object: `to_js({...}, dict_converter=Object.fromEntries)`. Its answer has `messageId`.
- Only an agreement with the status `DRAFT` can be deleted. A test that needs an active agreement gives it a policy and a basis.
- Service proposals (`specs/025-service-proposals/spec.md`): `process_proposals` in `src/app.py` is a job on the `RUNS` queue (a message holds `proposal_agreement_id`), started when a one-time agreement is completed. It runs fresh research and scoring, applies them, and emails the list. The variable `PROPOSAL_MODELS` is `DEFAULT` in production and `STUB` under `env.preview`, so the smoke test and the pipeline pay for no model. A real job is one call, on demand: `POST /api/v1/agreements/{id}/proposals?real=true`; it costs money, so say what it cost. Every start goes through `queue_proposals`, which records it in `agreement.proposals_started_at` and refuses a second start within `proposal.reuse_minutes` (`specs/036-proposals-once/spec.md`); `fresh=true` starts a job all the same. Inside that time a job uses a finished run again (`recent_run`) instead of paying for a new one, and sends no second email for the same start.
- A job with no request that needs code written for a request (`apply_scoring`, `audit`, `score_writes`) passes `job_request(env, "<job name>")`. Do not write that code a second time.
- The uptime checker (`specs/026-uptime-checker/spec.md`) is the scheduler's step `uptime_checks` in `src/app.py`: one check a day of each lead's and prospect's website until the company has `uptime.window_days` checks. Its numbers are settings (`uptime.*`), read first; the constants in `UPTIME_SETTINGS` are only the fallback. A check is `pages.check_site`, which never raises, and every write goes through `uptime_writes`, which also keeps the fact `uptime_percent`. "Is the site reliably up?" is answered from that fact by the measured rule; do not answer it anywhere else. The smoke test checks only a name under `.example`.
- A template is filled with `records.fill`, in one pass (`specs/033-audit-fixes/spec.md`): `ai.render` for a prompt, `notify.render` for an email. Never fill a placeholder with `str.replace`, and never look for braces after filling: text from outside may hold them. `ai.render` also takes the prompt's own tags out of every value, so a new prompt needs no extra care, and a new tag is covered when the prompt file uses it.
- A company's `domain` is `records.derive_domain(website, await shared_hosts(database))`. A page of a shared site (the setting `company.shared_hosts`: Facebook, Instagram, and others) gives no domain, so two businesses there are two companies. A website that cannot be read as an address is stored as given and skipped by `pages.site_url`; neither helper raises.
- `process_run` answers false when it could not record a failure, and the queue handler then calls `message.retry()`. A run whose result is stored is never changed to failed: a scoring run that cannot be started fails alone (`start_waiting`).
- A setting is read from the `setting` table on every use and changed with `PATCH /api/v1/settings` (`specs/016-settings/spec.md`). A new setting comes with a migration in `andexor-carmen-main` and, when its value has a form, a rule in `records.setting_problem`. Code keeps a fallback for a missing setting, never a second source of the value.
- All code passes strict type checking (`pyrightconfig.json`). Annotate every parameter and return value. JavaScript objects from the Workers runtime are typed `Any`, and the `js` module is reached through `access.js_module()`, because it exists only inside a Worker.
- Run `./unit-test.sh` for the type check and the unit tests. For a local run, put `DEV_USER_EMAIL=<email>` in `.dev.vars`; change the email to act as another user, and that user's role in the local database to test a role.
